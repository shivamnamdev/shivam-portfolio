# PRD 21: The learner portal reads the database (phase 5)

Status: slices 5a and 5b built 2026-11-06. Blueprint (approved): [docs/architecture/admin-portal-phase5-learner-portal.md](../../architecture/admin-portal-phase5-learner-portal.md). Later slices (5b learning content and private links, 5c banners, bell and templates, 5d prices and coupons) extend this PRD.

## 1. Flags
Four server environment variables (never `NEXT_PUBLIC_`), each `files` (the default) or `database`: `PORTAL_CATALOG`, `PORTAL_LEARNING`, `PORTAL_ENGAGEMENT`, `PORTAL_COUPONS`. Only the exact word `database` (any case) turns one on; any other value, a typo or an empty value means `files`. A flag set to `database` that cannot read its rows (error) or finds nothing published falls back to the data files **for that request**, logs one line without secrets, and never shows an error page. Turning a flag back to `files` is the rollback; nothing in the database changes. A change of a flag needs a restart or redeploy (it is read from the environment).

## 2. Slice 5a: the course list and sales pages (`PORTAL_CATALOG`)
Code: `lib/catalog/{source,tags,mapping}.ts` (pure, unit-tested) and `lib/catalog/catalog.ts` (server only); pages `app/courses/page.tsx` and `app/courses/[slug]/page.tsx`; `WhatsAppWidget` takes the support number as a prop. No SQL, no new package.

**Rules under test:**
* **Source:** with `files` the pages answer from `data/courses.ts` exactly as before and the database is never read. With `database` the list and pages are built from the **published** courses and cohorts (a cohort whose course is not published is not shown; drafts and archived items never appear). The QA fixture course (test environments only) stays available whichever source is on.
* **What is built:** the cohort gives identity, texts, status, price and the open or closed flag; the course's `pitch` gives only the known sales blocks (`vsl`, `painPoints`, `resources`, `differentiators`, `cohortHighlights`, `courseTestimonials`, `outcomes`, `bonuses`, `modules`). **A pitch can never set a slug, id, price, status, `listed` flag or link.** A block left out of the pitch stays absent (each sales component already hides or defaults a missing block).
* **Private links:** the live and WhatsApp links of a portal cohort are never read into the catalog: they are not in the page, the props or the HTML (slice 5b adds the access-checked route). After a purchase or free enrolment the success box takes the WhatsApp link from the server's reply (`verify-payment` already returned it; `enroll-free` now returns it too).
* **`listed`:** a cohort with `listed: false` is left out of `/courses` but its direct address still works (as today).
* **Price and open or closed follow the payment source** (the invariant "the amount shown equals the amount charged"): until `PORTAL_COUPONS` is `database` (slice 5d), orders are still priced from the data files, so a cohort that exists in the files shows the **file's** price and open flag, and a cohort that exists **only in the portal shows as closed** (the server could not charge it). When `PORTAL_COUPONS` is `database`, the portal's numbers and open flag are used. Prices are written like the site writes them (`₹1,999`, `$9.99`), a savings line only when there is a real saving, and a plans cohort shows its lowest plan until checkout learns plans (5d).
* **Support number:** the "chat with us" button uses the `support-phone` setting (digits only, India's 91 added to a plain 10-digit number; a number starting with 0 or an unusable one is ignored) and the long-standing default otherwise.
* **Freshness:** a saved change to a course, cohort or setting refreshes the cached list and pages at once (`revalidateTag('catalog')` after the audit entry is written); a 60-second timer is only a backstop.

**Unit (`tests/unit/catalog.spec.ts`):** `CAT-UNIT-SRC-001`, `002`, `CAT-UNIT-TAG-001`, `CAT-UNIT-MAP-001` to `006`, and the drift guard `CAT-UNIT-DRIFT-001` (what the portal would build from every real course in the data files equals the files: sales blocks, texts and price strings; links not carried).
**UI (`tests/ui/catalog/portal-catalog.spec.ts`, needs the server and the test run started with `PORTAL_CATALOG=database`, for example `PORT=3100 PORTAL_CATALOG=database E2E_SEED_PERSONAS=1 npx playwright test tests/ui/catalog`):** `CAT-UI-001` to `006` (empty portal falls back to the files; published items show, draft and unlisted do not; no private link in the HTML; portal-only cohort shows closed; change and setting show at once; unpublishing returns the files). Fixtures are `qa-cat-*`, removed afterwards; the support-phone setting is saved and restored.
**Matrix:** the existing public, discovery, sales-funnel and smoke suites are run with the flag `files` and again with `database` (nothing published, so the fallback answers): both must pass unchanged.
**Not automated:** the visual look of a page built from the portal; the production build's static generation (the list page is prerendered at build time and refreshed by the tag); a failure of the database in the middle of a request.

## 3. Slice 5b: lessons, the dashboard cards and the private links (`PORTAL_LEARNING`)
Code: `lib/catalog/learning.ts` (server only, with the pure `lessons.ts`), three learner routes `GET /api/learning/content/{slug}`, `/links/{slug}` and `/my-courses`; the lesson page, live lobby, dashboard, public share page and the certificate rule read through them. No SQL, no new package. The learner slug check now accepts `_` as the admin portal does.

**Rules under test:**
* **Source:** with `files` the lessons, titles and links come from `data/learning-content.ts` and `data/courses.ts` as before. With `database` they come from the cohort's **published** curriculum (never the draft) and its cohort and course documents (any status, so a finished cohort stays open to the people enrolled in it); a cohort with nothing published, or a database error, falls back to the files for that request.
* **Access check on the server:** `content` and `links` answer 200 only to a learner enrolled in that cohort or the admin, **403** to any other signed-in learner, **401** to a visitor, and **400** to a malformed slug; the answer to a refused caller holds none of the data. Nothing here depends on the page's own check any more.
* **Nothing private in the browser:** the lesson list, the lab, solution and expected-outcome links, and the live and WhatsApp links are no longer bundled with any page (the old pages imported both data files for every visitor). The sales page and the dashboard get no link in their props (in either source); the lesson page learns only **whether** a live class exists; the live lobby fetches the live link after the access check; the success box after a purchase or free enrolment uses the link in the server's reply. `/links` is never cached (`private, no-store`).
* **Dashboard:** `my-courses` returns the cards (id, slug, title, status text, duration, syllabus) of the learner's own enrolments in catalog order, no link; none held gives an empty list.
* **Share page and certificate:** the public share page names the lesson (the assignment title, or "Lesson n") and the course from the same source; the certificate percentage and course title use the same lessons as the lesson page.
* **Freshness:** a saved change to a curriculum, cohort or course refreshes the cached lessons, titles and cards at once (`revalidateTag('learning')`); links are read fresh.

**Unit (`tests/unit/catalog.spec.ts`):** `CAT-UNIT-MAP-007` (no private link in a page object), `CAT-UNIT-LES-001` (the lesson lookup equals the original code for every lesson in the files).
**API on the default server (`tests/api/learning-content.spec.ts`):** `LRN5B-001` to `006`. **With `PORTAL_LEARNING=database` (`tests/api/learning-content-db.spec.ts`, started as `PORT=3100 PORTAL_LEARNING=database E2E_SEED_PERSONAS=1 npx playwright test tests/api/learning-content-db.spec.ts`):** `LRN5B-DB-001` to `004` (portal lessons, title and live flag; links only to the enrolled learner; a publish and a link change show at once, an unpublished edit does not; the share page).
**Bundle (`tests/ui/learning/bundle-secrets.spec.ts`):** `LRN5B-BND-001` and `002`: the JavaScript files and the HTML the server sends for the sales pages, dashboard, lesson page and live lobby contain none of the private links, the first lesson id or the lab repository; the test also checks that enough JavaScript (including the lesson page chunk) was scanned.
**Matrix:** the dashboard, learning, learner-API and exam specs are run on the fixture server with all flags `files` and again with `database` (nothing published, so the fallback answers).
**Not automated:** how the lesson page looks for a portal-only cohort in the browser (the data path is covered by the API spec); the lesson page when the content route fails mid-session.
